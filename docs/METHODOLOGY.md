# Evaluation and benchmark methodology

## Dataset and accuracy

The committed `eval/questions.jsonl` has exactly 200 unique questions: 100 document,
70 SQL, and 30 clarification. The document questions are curated from the actual
15 fictional policy files, with six or seven specific facts per file. Each has a
one-sentence reference, one to three verbatim fact anchors, and a source filename.
The document and clarification seeds are committed separately; they are not
regenerated by a model. Clarification questions deliberately omit a subject.

`scripts/build_eval_set.py` preserves those seeds and generates SQL questions from
20 templates with varied parameters: counts, sums, averages, extrema, grouping,
date filters, and joins over the four demo tables. It executes every gold query
on the deterministic database, writing result rows into the reference answer.
The offline tests check every source anchor, gold query, count, and regeneration.

Routing accuracy is the fraction of expected route labels predicted correctly.
Answer accuracy follows Phase 2, independently of answer verbosity:

- SQL: execute the predicted SELECT and gold SELECT on the same database, comparing
  unordered row multisets with duplicate preservation and absolute numeric tolerance
  `1e-6`; unsafe, blocked, or errored queries are incorrect. Column aliases and answer
  wording do not affect the score.
- Document: require every anchor, case-insensitively; in Azure mode additionally ask
  the same chat model to judge reference versus candidate with an exact
  `CORRECT`/`INCORRECT` verdict. The fake mode uses only anchors.
- Clarification: require the clarify route and an answer ending in a question mark.

All profiles use these same scorers. The benchmark runs all 200 accuracy cases
unless `--limit` is explicitly supplied for a smoke check. The model judge itself
can be wrong or variable; anchor checks can reward irrelevant quoted text. These
are practical regression checks, not a complete measure of factual correctness.

## Paired profiles

`python -m eval.benchmark --provider azure` uses one process, one fixed SQLite dataset,
one chat/embedding provider configuration, and one isolated `eval_` Qdrant collection,
ingested once. Baseline runs first, optimized second. Baseline forces all optimization
flags off; optimized takes profile defaults and explicit environment overrides.
`TOP_K` still overrides each profile's default. Actual flags, deployments, question
IDs, source commit, and Actions run ID are saved in JSON. The router deployment,
when supplied, is the only intentionally different provider between profiles.

The accuracy runs use the configured `--workers` (default eight). Their timings
are retained separately and are **not** the headline latency result. Judging and SQL
result comparison are outside measured graph latency and token/cost accounting.

## Cold-work latency

A deterministic seed-42 sample selects `BENCH_LATENCY_N` questions (default 100,
capped to the available cases). Each profile gets three sequential passes with
workers=1. Before each pass, five warm-up questions run and are excluded; all local
answer, query-embedding, and schema caches are cleared again after warm-up.
The same subset and order are used across all passes and both profiles.

Headline mean, p50, and p95 are the median of the three corresponding per-pass
statistics, rather than a percentile of pooled concurrent observations. Mean tokens
and estimated cost are also the median of the three per-pass means. Raw request
records and all pass summaries remain available. Cold means empty local caches at
the start of a pass; schema and embedding caches may warm naturally during distinct
requests within that pass. No intentional question replays enter the headline.
Ingestion, graph construction, warm-up, and answer judging are excluded.

The optimized-only repeat scenario starts with cleared caches, runs the same subset,
then replays approximately 30% of those question IDs (at least one). Only the replay
requests determine its reported cache hit rate and mean latency. Clarification and
error responses are never cached, so a replay does not guarantee a hit. This separate
scenario must never be blended into cold latency or represented as a universal gain.

The comparison reports signed absolute and percentage changes in mean/p95 latency,
tokens, and estimated cost, plus the accuracy delta in percentage points. Percentage
change from a zero baseline is undefined and reported as null/N/A. The process fails
when accuracy drops by more than `BENCH_MAX_ACCURACY_DROP` (default 0.02, a fraction
or two percentage points). A slow optimized result is still reported honestly; no
speed improvement is guaranteed or manufactured by the implementation.

## Tokens and estimated cost

Azure metrics use API-reported usage and response model names, alongside deployment
names. Legacy custom providers remain compatible but return zero usage unless they
implement the optional usage interfaces. Fakes supply deterministic synthetic counts;
these are not billing or performance evidence. Cache hits use zero provider tokens.

`observability/pricing.py` contains illustrative USD-per-million input/output/embedding
rates for GPT-4o, GPT-4o-mini, and text-embedding-3-small/large. Override rates with
`PRICE_CHAT_INPUT_PER_M`, `PRICE_CHAT_OUTPUT_PER_M`, and `PRICE_EMBED_PER_M` to match
current pricing, agreements, and region. Unknown models use zero for missing rates
and issue a warning: zero does not mean free. Costs are estimates, not invoices.
They exclude ingestion, warm-up, judging, Azure hosting, Qdrant, Langfuse, and other
infrastructure. Failed attempts may have unobserved usage. Update prices before
making any monetary claim. Summary values truncate to eight significant digits;
raw JSON preserves measured precision.

## Observability and limits

Context variables isolate request metrics. Graph nodes, chat/embedding calls,
Qdrant retrieval, schema lookup, SQL execution, and cache hits are recorded. Only
`X-Debug-Metrics: 1` adds metrics to `/ask`; ordinary response fields stay unchanged.

Langfuse is optional, pinned to SDK 2.60.10 and implemented against its inspected
`trace`, `span`, and `generation` API. Without both keys it is a no-op. Completed
requests enter a bounded daemon-worker queue; overflow drops telemetry. The worker
constructs the SDK, exports, and flushes. SDK HTTP timeout is one second with no SDK
retries. Shutdown/eval flush waits at most 0.2 seconds per signal and cannot prove
remote delivery; an outage or abrupt process exit can lose traces. Tracing includes
questions, context, SQL, and answers; use only demo data until appropriate access and
data-handling controls are in place.

This is a small synthetic dataset, not held-out enterprise production traffic.
One region, model/deployment choices, Azure quota, network variance, CPU scheduling,
connection reuse, baseline-first ordering, and optional telemetry can affect results.
A cheaper router may hurt quality. Parallelizing tiny local work may be slower.
There are no confidence intervals or broad generalization guarantees here.

## Describe results honestly

State the provider/model deployments, commit, run ID, dataset size, region, flags,
pricing assumptions, and measurement method. Quote actual output files and show
quality changes alongside latency/cost changes. Label the repeat-traffic scenario
separately. Do not present fake-provider timings as Azure speedups, a single-region
sample as a universal result, or estimated costs as billed savings. The README stays
pending until complete real-Azure outputs exist; the renderer rejects fake results.
